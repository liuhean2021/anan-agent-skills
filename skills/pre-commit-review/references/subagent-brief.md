# 零上下文审查子 agent 说明模板

主 agent 每次审查时按本模板组装说明，交给一个**新建的、零上下文**的子 agent 执行。只填下方「输入字段」，不追加任何其他内容。

## 输入字段（主 agent 填写）

| 字段 | 说明 | 示例 |
|------|------|------|
| `REPO` | 仓库根目录绝对路径 | `/path/to/repo` |
| `SKILL` | 本技能 `SKILL.md` 的绝对路径 | `/path/to/skills/pre-commit-review/SKILL.md` |
| `DIFF_RANGE` | 审查范围，三选一或组合 | `staged` / `worktree` / `<base>..HEAD` |
| `REQUIREMENT` | 需求原文：用户原话、issue 文本，或 spec / 需求文档路径；没有则写「未提供」 | `specs/001-login/spec.md` |
| `OUTPUT` | 审查文档输出路径；未指定写「默认」，按 SKILL.md 第五步执行 | `specs/001-login/review-findings.md` |
| `ROLE` | 审查角色：`主审` / `交叉复核-A` / `交叉复核-B` | `主审` |

## 禁止传入

- 主 agent 的实现思路、设计取舍解释、「我觉得没问题」等判断
- 上一轮或其他子 agent 的审查结论（修复后复审同样不传）
- 对话历史摘要、开发者对代码的辩护

> 需求原文是「要做什么」，实现思路是「为什么这么写」——只传前者。审查者要独立判断代码是否满足需求，而不是确认作者的思路。

## 说明正文（原样使用，替换 `{}` 占位）

```text
你是一名独立代码审查者，对本次改动没有任何先验认知。

仓库：{REPO}
审查范围：{DIFF_RANGE}
需求：{REQUIREMENT}
输出路径：{OUTPUT}
角色：{ROLE}

1. 先完整阅读 {SKILL}，按其执行步骤审查。
2. 角色为「主审」：执行第一步至第 4.3 步，以及第五步（写审查文档）、第六步（learnings）。
   角色为「交叉复核-A / B」：只按 §3.12 对应视角的清单审查，不写审查文档、不写 learnings，只返回发现列表（来源标注为〔交叉复核-A〕/〔交叉复核-B〕）。
3. 只读审查，绝不修改业务代码；可写的文件仅限审查文档与 learnings.jsonl。
4. 以下事项你无法与开发者对话，不要自行假设，写入返回结果的「待确认」：
   - §2.7 架构定性任一为「否」，需要开发者确认方向
   - 代码读不懂、需开发者澄清之处
   - §4.3 判定 Self-Test SHOULD / MUST 执行（只给判定与理由，不出题）
5. 返回结果（中文，按以下结构）：
   - 审查结论：通过 / 不通过（不通过须逐条列出 🔴 原因，带 文件:行号）
   - 问题统计
   - 待确认（无则写「无」）
   - 交叉复核建议（主审）：§1.5 负载告警是否触发、触发了哪项 → 是否建议执行 §3.12（只给建议，是否执行由用户决定）
   - Self-Test 判定：不触发 / SHOULD / MUST + 理由
   - 审查文档路径（主审）
```

## 主 agent 收到结果后

- 原样转述审查结论与 🔴 原因，不改写、不弱化。
- 「待确认」逐项问开发者；架构方向被否定或代码需澄清时，开发者回复后**新建**子 agent 重审，不复用原子 agent。
- 交叉复核**默认不执行**：主审建议执行时，向用户说明触发的告警并询问是否交叉复核；用户明确同意后才并行新建「交叉复核-A / B」两个子 agent（任一时刻最多并行 2 个），按 SKILL.md §3.12 合并发现并补入审查文档；未同意则在审查文档注明「交叉复核：建议执行，用户未确认，未执行」。
- Self-Test 判定为 SHOULD / MUST 时，由主 agent 执行 SKILL.md §4.4。
