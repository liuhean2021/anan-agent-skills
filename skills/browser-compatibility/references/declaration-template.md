# 项目兼容声明模板

项目内的兼容声明（建议 `docs/browser-compatibility.md`）**只记录兼容范围**：不写决策过程、实现原理、所用技能或标准来源——这些属于审查报告，不进项目文档。多端项目（PC + H5）可每端一张表。

```markdown
# 浏览器兼容范围

适用:<应用 / 目录>(<PC / H5>)    更新日期:<YYYY-MM-DD>

| 浏览器 / 环境 | 最低版本 |
|---------------|---------|
| Chrome / 国产双核浏览器(极速模式) | <版本> |
| Edge | <版本> |
| Firefox | <版本> |
| Safari | <版本> |
| iOS(含 App 内 WebView) | <版本> |
| Android Chrome / WebView | <版本> |
| 微信 / UC / QQ 等 | <已实测 / 未实测> |

**不支持**:<浏览器>(<一句话原因>)

**功能级可用范围**(可选,某功能要求高于上表基线时填写,如依赖 module Worker / WASM 的预览、解压、编辑器):
- <功能名>:需 <浏览器 ≥ 版本>;低于时 <表现,如「回退为下载」>(<已实测 / 未实测>)

**兼容等级**(可选):基线内全部环境保证「核心可用」;<环境> 达到「体验完整」;毛玻璃等增强效果按特性检测启用(等级定义见技能 standard.md §9.5,声明中只写结论)

**已知限制**:
- <版本区间>:<表现>(如「Chrome 64–83:部分间距与样式有偏差,功能正常」)
```

写法要求：

- **写用户看到什么**，不写技术术语堆砌：如「操作列里相邻的两个文字按钮间距消失、看起来连成一个词，仍可分别点击」，而不只是「flex gap 不支持」。
- **不修的决定写明日期与决策人**：如「<日期> <决策人> 决定不接入错误上报」；大批量问题（如几十处 flex `gap`）一次性改代价过高时，登记为已知限制并写明「维持不修」及原因。
- **未实测的写「未实测」**：基线版本、功能级可用范围、App 内表现没有真机验证时如实标注，实测后再定稿。
- **多应用共用基线**（monorepo、模板生成的新应用）：写「沿用 <应用> 已审基线」并逐项列出比对依据（构建兼容配置、`index.html` head、全局样式、关键依赖版本一致），并写明改动其中任一项须重新审查（architecture.md §2.1）。

只保留与项目相关的行；删除不适用的端。基线调整、依赖升级或审查中用户决定不修复的问题，更新本表与「已知限制」。
