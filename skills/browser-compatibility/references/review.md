# 兼容性审查与修复建议

> 本技能负责**实际的兼容审查**并给出修复建议；pre-commit-review §3.13 只做兼容性声明，需要检查时转交本技能。
> **修复铁律：审查阶段只读（唯一例外：写入审查报告文档，见 §7），任何代码、配置、依赖的修改 MUST 先获得用户明确确认。**

## 1. 审查范围

| 模式 | 触发 | 范围 |
|------|------|------|
| **变更审查** | 提交前、PR、pre-commit-review 转交 | 本次 diff 涉及的源码 / 样式 / 构建配置 + 本次构建产物 |
| **全量审查** | 接手项目、升级框架或组件库、调整兼容基线 | 构建配置 + 全部源码 + 完整构建产物 |

## 2. 确定兼容范围（先定范围，再审查）

1. **项目声明优先**：兼容声明文档、`.browserslistrc`、`package.json` 的 `browserslist`、`vite.config.*` 的 `build.target` / `@vitejs/plugin-legacy` 的 `targets` / `modernTargets`、`@babel/preset-env` 的 `targets`、需求文档或 PRD 的兼容约束。
2. **未声明时，默认基线 = 技术栈硬下限（覆盖率最大化）**：按 standard.md §3 取项目实际依赖（框架、组件库、构建工具、关键三方库）官方下限的最高者，并在结论中给出 🟢 建议「补充兼容声明」。常见技术栈参考：

   | 技术栈 | 硬下限（最大覆盖） | 需要的方案 |
   |--------|------------------|-----------|
   | PC：Vite + Vue 3 + Element Plus | Chrome 64 / Edge 79 / Firefox 78 / Safari 12 | B |
   | H5：Vite + Vue 3 + Vant 4 | Chrome 51 / iOS 10（Vue 3 下限） | C（低于 Vite 原生 ESM 下限） |
   | Vue 2 / React ≤ 17 | 含 IE 11 | C 或 D |

   两端均须：国产双核浏览器极速模式（PC）；微信 / UC / QQ 等 App 内 WebView 列为必测环境（H5）。

3. **声明高于硬下限（存在覆盖空间）**：按项目声明审查，同时在发现中记 🟡「基线可下探至 <硬下限>，预计多覆盖 <x%>」，给出所需方案与代价，由用户决定是否下探。
4. **配置与声明必须一致**：声明 Safari 14 但构建 target 为 `esnext` 且无 polyfill，等于没有兼容——记为 🔴 或 🟡（见 §4）。

视口与显示范围（用于人工 / 运行验证）：
- PC：1280 / 1366 / 1440 / 1920 / 2560 宽；缩放 100% / 125% / 150%；Windows 与 macOS。
- H5：320 / 360 / 375 / 390 / 414 / 430 宽；平板 768 / 820 / 1024；横竖屏；DPR 2 / 3；刘海屏与底部安全区；系统字体放大；厂商强制暗色。

## 3. 审查步骤

| 步骤 | 内容 | 依据 |
|------|------|------|
| ① 配置审查 | 构建目标、legacy 插件 / Babel / core-js、autoprefixer、PC 双核 meta、H5 head 配置是否与基线一致；所选方案能否达到硬下限 | standard.md §4；pc.md §2；h5.md §3 |
| ①′ 覆盖空间审查 | 基线是否已压到硬下限；standard.md §8 的扩大覆盖手段（DOM API polyfill、CSS 降级、依赖转译、端专项配置）是否已启用；用 browserslist 量化可多覆盖的比例 | standard.md §3 / §4 / §8 |
| ② 产物检查 | 构建到临时目录，运行 `scripts/check-browser-compat.mjs` | SKILL.md「产物检查」 |
| ③ 源码审查 | 对变更或全量源码逐项排查高发问题（下表） | standard.md §5；pc.md §3；h5.md §5 |
| ④ 运行验证 | preview / 测试环境 / 真机 / App 内实测；无法执行时标注「未运行验证」 | pc.md §6；h5.md §8 |
| ⑤ 影响评估 | **每个发现**都要评估受影响浏览器区间、用户占比、实际表现，得出紧急度，供用户排修复优先级 | 本文 §4.1 |

源码审查的快速检索（在 `src/` 下执行，命中后逐条人工判断，**不得仅凭命中下结论**）：

| 检索 | 风险 |
|------|------|
| `new Date\(['"\`]\d{4}-\d{2}-\d{2} ` | Safari / iOS 日期解析为 Invalid Date |
| `/\(\?<[=!]` （正则字面量） | Safari / iOS < 16.4 白屏 |
| `\.at\(\|structuredClone\|replaceAll\|Object\.hasOwn\|findLast` | 基线低于 standard.md §5.2 时需 polyfill |
| `gap:\|:is\(\|:has\(\|aspect-ratio\|inset:\|@container\|color-mix` | CSS 退化（standard.md §5.3） |
| `100vh` | H5 底部被遮挡 |
| `:hover` 且无触屏入口 | H5 无法触发 |
| `window\.open\|download=\|autoplay` | App 内 WebView 受限（h5.md §4） |
| `navigator\.userAgent` | UA 判断失效（iPadOS 伪装 Mac） |

## 4. 定级

| 情况 | 等级 |
|------|------|
| 目标范围内**白屏**（语法超标、正则后行断言字面量、入口处缺 API）、脚本报错、核心路径无法完成（无法提交、无法支付、按钮被遮挡且点不到） | 🔴 |
| 目标范围内明显布局错乱、功能降级无提示；构建配置与声明不一致但暂未造成白屏；高风险项未经运行验证；**基线高于硬下限或扩大覆盖手段未启用（存在覆盖空间）** | 🟡 |
| 视觉细节差异、非核心页面降级体验、未写兼容声明 / 未声明 browserslist | 🟢 |

检查脚本输出与等级的对应：`✗` → 🔴；`⚠` 字符串后行断言 → 追溯后可达则 🔴、不可达则记录即可；`⚠` CSS → 按影响页面与布局判断 🟡 / 🟢。

### 4.1 影响评估（MUST，每个发现都做）

目的：让用户判断「修不修、先修哪个」。等级（🔴🟡🟢）回答「问题性质多严重」，影响评估回答「波及多少人、紧急到什么程度」，两者都要给。

**① 受影响浏览器区间**：由「基线下限」到「该特性最低支持版本 − 1」（查 standard.md §5）。例：基线 Chrome 64，flex `gap` 需 Chrome 84 → 受影响区间 Chrome 64–83；同理列出 Edge / Safari / Firefox / iOS / Android。

**② 用户占比**（优先级：项目自有访问统计 > browserslist 估算）：

```bash
# 受影响区间占全部用户、以及占「支持范围内用户」的比例(后者更能说明对本项目用户的影响)
AFFECTED="chrome 64-83, edge 79-83, safari 12-14.0"      # 按 ① 填写
SUPPORTED="chrome >= 64, edge >= 79, firefox >= 78, safari >= 12"  # 项目基线
npx browserslist@latest --coverage "$AFFECTED";      npx browserslist@latest --coverage "$SUPPORTED"
npx browserslist@latest "--coverage=CN" "$AFFECTED"; npx browserslist@latest "--coverage=CN" "$SUPPORTED"
```

- 报告同时给「全球 / 中国」两组数，以及「占支持范围内用户的比例 = 受影响 ÷ 支持范围」。
- H5 的分母用「全部移动用户」口径（h5.md §6）。
- zsh 下 `--coverage=CN` 必须加引号，否则 `=CN` 会被当作命令路径展开导致报错。
- **数据局限必须写明**：caniuse 为公网统计，政企内网（老内核 360 等）、特定 App 内 WebView 的真实占比可能显著更高；有项目访问统计时以统计为准，没有时提示用户补充。

**③ 实际表现**（尽量用证据而非描述）：
- 功能层面：白屏 / 功能不可用 / 功能可用但体验下降 / 仅视觉。
- 能在现代浏览器模拟的就模拟并截图对比，例如：
  | 问题 | 模拟方式 |
  |------|---------|
  | flex `gap` 不支持 | 遍历元素，对 `display: flex / inline-flex` 且 gap 非 0 的容器设 `gap: 0 !important` |
  | 选择器特性（`:is()` / `:has()` / `:focus-visible`）不支持 | 临时禁用包含该选择器的样式规则，或用键盘 Tab 走查聚焦态 |
  | CSS 属性不支持（`aspect-ratio`、`inset` 等） | 对命中元素移除该属性 |
- 模拟后 MUST 恢复页面状态；无法模拟的标注「未模拟，需真机确认」。
- 同时核实**是否真的会触发**：受影响的组件 / 页面是否被项目实际使用（如只存在于未使用组件中的规则，影响为无）。

**④ 紧急度**（默认阈值，项目可按用户群调整）：

| 紧急度 | 条件 |
|--------|------|
| **P0 立即修** | 白屏或核心路径不可用（无论占比） |
| **P1 尽快修** | 功能受损（可用但易误操作、关键信息难辨认）且占比 ≥ 1%；或已知内网存在大量受影响终端 |
| **P2 排期修** | 纯视觉退化且占比 ≥ 1%；或功能受损但占比 < 1% |
| **P3 可不修** | 纯视觉且占比 < 1%；仅影响键盘 / 辅助场景且修复代价高；受影响组件未被使用 |

## 5. 输出格式

```markdown
## 兼容性审查报告

### 范围
- 模式：变更审查 / 全量审查
- 端：PC / H5 / 两者
- 基线：<来源(项目声明 / 硬下限)> — <浏览器与版本>；技术栈硬下限：<浏览器与版本>；覆盖空间：<无 / 可下探至 … 多覆盖 x%>
- 产物检查：`check-browser-compat.mjs --ecma <> --min <>` → 退出码 <>

### 发现
| # | 等级 | 紧急度 | 端 | 来源 | 位置 | 问题 | 受影响浏览器 | 用户占比（全球 / 中国；占支持范围） | 实际表现 | 修复建议 |
|---|------|--------|----|------|------|------|-------------|-----------------------------------|---------|---------|
| 1 | 🔴 | P0 | PC | 产物 | assets/index-xxx.js | 含 `?.`，基线 Chrome 64 不支持 | Chrome 64–79 | 0.3% / 1.1%；占支持范围 2.9% | 整页白屏 | 启用 legacy 插件 `modernTargets` … |
| 2 | 🟡 | P2 | H5 | 源码 | src/pages/a.vue:42 | `height: 100vh` | iOS 全版本(地址栏行为) | —（行为问题，与版本无关） | 底部按钮被工具栏遮挡（截图） | 改为 `100dvh` 并保留 `100vh` 回退 |

（来源取值：配置 / 产物 / 源码 / 运行；用户占比注明数据来源：项目统计 / browserslist 估算及日期）

### 影响汇总
- 按紧急度排序列出各发现，并给出「建议修 / 可不修」的理由（结合占比、表现与修复代价）。
- 数据局限：<公网统计与本项目用户群的差异；是否有项目访问统计>

### 未运行验证的高风险项
- …

### 修复方案（待确认）
1. [对应发现 #1] <改动内容、涉及文件、是否新增依赖、预计影响>
2. [对应发现 #2] …

请确认要执行的修复编号（如「1、2」「全部」「都不改」）。
```

- 每条修复建议 MUST 写清：改哪些文件、改成什么、是否新增依赖或修改构建配置、对包体积 / 构建时间的影响、如何验证。
- 同一问题有多种解法时（如「调低转译目标」vs「替换依赖」），列出选项与取舍，不替用户做决定。

## 6. 修复确认规则（MUST）

1. **审查阶段只读**：不修改任何源码、样式、构建配置、`package.json`、锁文件、`index.html`（审查报告文档除外，见 §7）。
2. **逐项确认**：只执行用户明确确认的修复编号；「全部」只覆盖报告中列出的项，不得顺带做未列出的改动。
3. **高影响项单独确认**：新增 / 升级依赖、修改构建目标、引入 polyfill 包、改动全局样式时，即使用户说「全部」，也要在执行前复述影响并再次确认。
4. **修复后复验**：重新构建并运行检查脚本，对比修复前后结果；涉及运行时行为的，重做运行验证。
5. **不代为提交**：修复完成后报告结果，是否提交由用户决定。
6. 用户选择「不改」的发现，写入项目兼容声明的「已知限制」。
7. 修复完成后，在审查文档中补记「修复回执」（执行了哪些编号、复验结果）。

## 7. 审查文档（MUST）

审查结果必须写成文档存入项目，便于留痕、评估与后续复审。

| 项 | 约定 |
|----|------|
| 位置 | 项目已有 `docs/review/` → `docs/review/browser-compatibility-review.md`；否则 `docs/browser-compatibility-review.md`（目录不存在则创建）。上层工作流指定了路径时按其路径 |
| 数量 | **每个项目一份**；多端项目在同一文档内按端分节 |
| 更新方式 | 每次审查在文档末尾**追加**一节 `## <YYYY-MM-DD> <变更审查/全量审查>（<端>）`，不改写历史节；文档顶部「最新结论」摘要随之更新 |
| 内容 | §5 输出格式的全部内容：范围、已确认无问题项、发现（含影响评估）、影响汇总、未运行验证项、修复方案与用户决定；有截图对比时写明模拟方式与结论 |
| 修复回执 | 用户确认并执行修复后，在对应节补记执行编号、改动文件、复验结果（产物检查前后对比） |
| 与兼容声明的关系 | 兼容声明（`docs/browser-compatibility.md`）只记兼容范围；原因、数据、过程都写在审查文档，声明中不引用审查文档细节 |
| 索引 | 项目有 `docs/review/README.md` 等索引时，登记本文档 |

文档骨架：

```markdown
# 浏览器兼容性审查记录

## 最新结论
- 日期 / 模式 / 端:…
- 白屏级问题:<n>;待修复:<编号与紧急度>;已接受的限制:<…>

## <YYYY-MM-DD> 全量审查(PC)
(按 §5 格式)
### 修复回执
(如有)
```
