# 移动端 H5 专项

> 通用部分见 [standard.md](standard.md)。数据核对于 2026-09。内置 WebView 的内核与能力随宿主 App 版本变化，**MUST 在目标 App 内实测**，本文仅作起点。

## 1. 运行环境与内核

| 环境 | 内核 | 版本由什么决定 | 要点 |
|------|------|--------------|------|
| iOS / iPadOS 上的**所有**浏览器（含 Chrome、Edge、微信、企业微信、钉钉内打开） | WebKit（WKWebView） | **iOS 系统版本**（Safari 版本 ≈ iOS 版本） | 用户不升级系统，浏览器能力就不升级；基线按 iOS 版本写 |
| Android Chrome | Blink / Chromium | Chrome 自身版本 | |
| Android System WebView（各 App 内嵌页） | Chromium | 通过应用商店更新；**国内无 Google Play，版本取决于厂商 ROM 更新，可能明显偏旧** | 基线按 Chromium 版本写 |
| 微信（Android） | XWeb（Chromium）；老设备 / 老版本为 X5（TBS） | 随微信版本下发 | UA 含 `XWEB/` 或 `TBS/`；实际 Chromium 版本看 UA 中 `Chrome/xx` |
| 企业微信 / 钉钉 / 支付宝等（Android） | 各自内置或系统 WebView（历史上有 UC U4 等自研内核） | 随 App 版本变化 | 必须在目标 App 内用 `navigator.userAgent` 实测 |
| UC / QQ 浏览器（Android） | 自研内核（UC U4、腾讯 X5，均基于较旧 Chromium 分支） | 随浏览器版本 | **不能按 Chrome 版本推算**，需单独实测 |
| iPadOS 13+ | WebKit | 同 iOS | 默认以桌面 UA 访问（伪装成 Mac），UA 判断会失效 |
| 鸿蒙微信 / 鸿蒙系统浏览器 | 鸿蒙系统 WebView（内核与版本以真机为准） | 鸿蒙系统 / 微信版本 | UA 含 `OpenHarmony`（微信内另含 `MicroMessenger`）；UA 特征与 iOS / Android 不同，见下「识别微信环境」；必须真机实测 |

## 2. 基线（默认 = 技术栈硬下限，覆盖率最大化）

| 技术栈 | 硬下限 | 方案（standard.md §4） |
|--------|--------|----------------------|
| Vite + Vue 3 + Vant 4 | Chrome 51 / iOS 10（Vue 3 下限） | **C**（低于 Vite 原生 ESM 下限 iOS 11.3 / Chrome 64，只用 B 会丢掉这一段） |
| Vite + React 18 | 框架下限低于 Vite 原生 ESM 下限 | C |
| Vue 2 + Vant 2 | Android 4.0+ / iOS 8+ | C 或 D |

- 国内项目在所选基线之外，**UC / QQ 浏览器、微信（含 X5）MUST 列为必测环境**（自研内核，无法按版本推算）。
- 仅当业务明确不需要老版本时才上调（如 iOS ≥ 14 / Android ≥ 87，方案 A），并在审查报告中记录被放弃的覆盖率。

## 3. 必做配置：移动端 head

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
<meta name="format-detection" content="telephone=no, email=no" />
```

- `viewport-fit=cover` 配合 `env(safe-area-inset-*)` 适配刘海屏与底部 Home 指示条。
- `format-detection` 防止 iOS 把数字串识别为电话号码并改写样式。
- **不建议**用 `user-scalable=no` / `maximum-scale=1` 禁止缩放（影响无障碍）；iOS 聚焦放大问题用「输入框字号 ≥ 16px」解决。

## 4. App 内 WebView 的能力限制（以微信为代表）

| 能力 | 常见限制 | 替代路径 |
|------|---------|---------|
| 文件下载 | 直接下载无响应或被拦截 | 提供在线预览；或引导「在浏览器中打开」 |
| `window.open` / 新窗口 | 被拦截或在当前页打开 | 当前页跳转；返回路径要可用 |
| 视频/音频自动播放 | 需用户交互触发 | 首次交互后播放；按平台文档处理（如微信 JS-SDK / `WeixinJSBridgeReady`） |
| `<input type="file">` | `accept` / `capture` / 多选行为与系统浏览器不同 | 目标 App 内逐项实测；必要时用平台 JS-SDK 选择图片 |
| 跳转其他 App / scheme | 受平台限制 | 使用平台开放能力（如微信开放标签） |
| 页面缓存 | HTML 被强缓存，发版后用户仍看旧页面 | 静态资源带 hash；HTML 设置 `no-cache` 或加版本参数 |
| 返回页面 | bfcache 恢复时不重新执行初始化 | 监听 `pageshow`（`event.persisted`）刷新必要状态 |
| 剪贴板 | `navigator.clipboard` 在非安全上下文或部分 WebView 不可用 | 回退 `document.execCommand('copy')` |

### 识别微信环境

均基于 `navigator.userAgent`，**先转小写再匹配**（用于在报告中确认「已在目标环境实测」、或做环境专属降级）。官方依据：[鸿蒙网页开发适配指南](https://developers.weixin.qq.com/doc/subscription/guide/h5/adapt_harmonyos.html)。

| 环境 | 判断 | 说明 |
|------|------|------|
| 微信 | `/micromessenger/.test(ua)` | 核心标识；iOS、Android、鸿蒙微信**都**带；**企业微信也带**，所以它在企业微信里同样为 true |
| 鸿蒙微信 | `/openharmony/.test(ua) && /micromessenger/.test(ua)` | 官方：UA 须**同时**含 `OpenHarmony` 与 `MicroMessenger`；UA 特征与 iOS / Android 不同，可能导致网页功能异常，需主动适配 |
| 企业微信 | 先判微信，再判 `wxwork`：`/micromessenger/.test(ua) && /wxwork/.test(ua)` | 企业微信是微信内核环境的子集，**先确认是微信（`MicroMessenger`），再看是否含 `wxwork`**；普通微信 = 微信且不含 `wxwork` |

```js
const ua = () => navigator.userAgent.toLowerCase()
const isInWeiXinBrowser = () => /micromessenger/.test(ua())                            // 微信（含企业微信、鸿蒙微信）
const isInHarmonyWeChat = () => /openharmony/.test(ua()) && /micromessenger/.test(ua()) // 鸿蒙微信
const isInWxWork = () => isInWeiXinBrowser() && /wxwork/.test(ua())                    // 企业微信（先判微信，再判 wxwork）
```

- 需要区分移动端 / PC 端企业微信或微信时，再叠加移动端 UA 特征（`Mobile` / `Android` / `iPhone` 等）判断，不要单靠 `wxwork`。
- 鸿蒙微信另有两点官方提示：① 用 `wx.checkJsApi` 判断当前客户端是否支持指定 JS 接口，不支持时在业务层兼容；② 微信支付在鸿蒙微信 1.0 起支持，**不要拿「微信版本号 ≥ 5.0」这类判断卡支付**，须针对鸿蒙微信适配。
- 微信官方另有「iOS WKWebview 网页适配」「DarkMode 适配」两篇网页适配文档，审查 iOS 微信与暗色场景时一并参考。
- 鸿蒙微信的内核与版本能力**以真机为准**，不要按 Chrome / iOS 版本推算；MUST 列入必测环境（与 UC / QQ 同级）。
- Android 微信 UA 另含 `XWEB/` 或 `TBS/`（内核标识），Chromium 版本看其中的 `Chrome/xx`；iOS 微信内核恒为 WebKit，版本取决于 iOS 系统。
- 审查报告须记录**实测时的完整 `navigator.userAgent`**，不要仅凭「含 MicroMessenger」推断内核能力。

## 5. 移动端高发问题

| 问题 | 典型表现 | 审查要点 |
|------|---------|---------|
| `100vh` | 地址栏/工具栏导致底部被遮挡 | `dvh` / `svh`（iOS 15.4+）并保留 `vh` 回退；**`vh` 必须写在 `dvh` 之前**，写反（`100dvh; 100vh;`）时后者覆盖前者，`dvh` 形同虚设；`grep -rn -B1 '100vh' src` 逐处核对顺序 |
| 安全区 | 刘海屏、Home 指示条遮挡按钮 | `viewport-fit=cover` + `env(safe-area-inset-*)` |
| iOS 输入框自动放大 | `font-size < 16px` 聚焦时页面放大 | 输入框字号 ≥ 16px |
| 软键盘 | 底部 `position: fixed` 错位、输入框被遮挡 | 处理 `visualViewport`，或输入场景避免 fixed |
| 只靠 hover 的交互 | 触屏无法触发或关闭 | `@media (hover: hover)` 区分，提供点击入口 |
| 点击区域过小 | 误触、点不中 | 可点击区域 ≥ 44×44px |
| 滚动穿透 | 弹窗内滑动带动底层页面 | 锁定 body 滚动，`overscroll-behavior: contain` |
| 横向溢出 | 320px 宽出现横向滚动 | 长文本、表格、图片换行或容器内滚动 |
| UA 判断失效 | iPadOS 被识别为 Mac | 特性检测（`navigator.maxTouchPoints`、`matchMedia`） |
| 日期解析 | iOS 上 `new Date('2026-09-26 10:00')` 为 Invalid Date | ISO 格式或日期库 |
| 图片格式 | WebP 在 iOS < 14、AVIF 在 iOS < 16 不显示 | `<picture>` 提供回退 |
| 高 DPR | 1px 边框显粗、位图模糊 | `srcset`、矢量资源 |
| 强制暗色、字体放大（含微信「字体大小」、系统「显示与文字大小」） | 厂商浏览器反色、字体放大撑破布局、被截断 | `color-scheme` 声明；文本容器用 `min-height`/`max-height` 而非固定 `height`，少用 `nowrap`；`html` 加 `text-size-adjust: 100%` 抑制 iOS 横屏自动放大。**可在浏览器模拟**：视口 320px，遍历元素把 `font-size` ×1.3 后检查 `scrollWidth > innerWidth` 与 `overflow:hidden` 元素 `scrollWidth > clientWidth`；微信 Android 的字体缩放由 WebView `textZoom` 完成，仍需真机确认 |
| 横屏访问（H5 **默认按竖屏**使用） | 手机横屏后布局被压扁、固定底栏与弹层遮挡内容；网页无法真正锁屏 | 默认检查是否有横屏处理（遮罩提示），见 §5.1 |
| 横竖屏切换 | 布局错乱、弹层位置错误 | 监听尺寸变化并重新计算 |

### 5.1 横屏策略（默认竖屏，MUST 检查）

**H5 默认按竖屏设计与使用**：除非项目明确声明支持横屏，审查时默认检查「是否禁止 / 处理了横屏」，并在报告中写明结论。

**网页无法真正锁屏**，只能在横屏时遮挡并提示用户转回竖屏：

| 手段 | 能否用于 H5 | 说明 |
|------|------------|------|
| `@media (orientation: landscape)` 遮罩提示 | ✅ 推荐 | Chrome 3+ / Safari 5+（iOS 5+，数据：MDN browser-compat-data），覆盖基线 iOS 10 / Chrome 51 |
| `screen.orientation.lock('portrait')` | ❌ 基本不可用 | 仅全屏或已安装的 PWA 可用；iOS Safari 不支持；微信 WebView 基本无效 |
| PWA manifest `"orientation": "portrait"` | ❌ 对微信内链接无效 | 只对「添加到主屏幕」打开的情况有效 |
| 宿主 App 锁定方向 | ✅ 最彻底 | 由宿主（主应用 / 小程序 `pageOrientation`）控制，网页侧无法实现 |

推荐实现（半透明全屏遮罩 `.rotate-tip` 置于路由出口之后，**显示条件由 CSS 控制、关闭由一个布尔状态控制**）：

```html
<div v-if="!dismissed" class="rotate-tip" role="alert">
  <svg class="rotate-tip__icon" aria-hidden="true">…</svg>
  <p class="rotate-tip__text">请将手机竖屏使用</p>
  <button type="button" class="rotate-tip__close" @click="dismissed = true">继续横屏使用</button>
</div>
```

```css
.rotate-tip { display: none; }
@media (orientation: landscape) and (max-height: 480px) {
  .rotate-tip {
    display: flex; position: fixed; left: 0; top: 0; right: 0; bottom: 0; /* 不用 inset：iOS < 14.1 不支持 */
    z-index: 9999; align-items: center; justify-content: center; flex-direction: column;
    background: rgba(0, 0, 0, 0.6); color: #fff; /* 半透明：隐约可见页面，文字用白色保证可读 */
  }
  .rotate-tip__close { min-height: 44px; padding: 0 20px; border: 1px solid rgba(255,255,255,.8);
    border-radius: 999px; background: transparent; color: #fff; }
}
```

- **`max-height: 480px` 不能省**：① 把平板横屏排除在外（平板横屏是正常用法）；② 部分安卓浏览器软键盘弹出时视口宽高比会一度变成横向，只判断 `orientation` 会误触发。
- **必须允许用户关闭**（「继续横屏使用」按钮）：强制挡住会让确实需要横屏的用户（外接键盘、看宽表格、横屏更舒服）无法使用。关闭状态只放内存（本次访问有效，刷新后重新提示），不必持久化。
- 背景用**半透明**而非纯白：不挡死页面；不要完全透明，白字叠在页面上看不清。
- 遮罩元素加 `role="alert"`；文案「请将手机竖屏使用」；关闭按钮点击区域 ≥ 44px。
- 遮罩下的页面在手机上仍可能滚动，不影响使用；需要彻底时再锁 body 滚动。

**审查方法**：

```bash
# 源码里是否有横屏处理
grep -rnE 'orientation:\s*landscape|screen\.orientation|rotate-tip|"orientation"' src public index.html
```

| 结果 | 定级 / 处理 |
|------|------------|
| 有遮罩，且 852×393、568×320 横屏显示、393×852 竖屏与 1024×768 平板横屏**不**显示，**点关闭按钮后遮罩消失** | ✅ 通过 |
| 有遮罩但**没有关闭入口** | 🟢 建议补「继续横屏使用」按钮（强制挡住会让需要横屏的用户无法使用） |
| 无横屏处理，项目**未**声明支持横屏 | 🟡 P2（横屏下固定底栏 / 弹层 / 首屏布局易被压扁）；给出遮罩方案，由用户确认后修复 |
| 项目**声明支持横屏** | 不要求遮罩；改为验证横屏布局可用（视口 568×320、852×393，固定底栏不遮挡输入区） |
| 用户明确「不限制横屏」 | 🟢，写入兼容声明「已知限制」 |

运行验证：用 Playwright 把视口依次设为 393×852（竖屏）、852×393（手机横屏）、568×320（小屏横屏）、1024×768（平板横屏）、768×1024（平板竖屏），读 `getComputedStyle(遮罩).display`：仅手机横屏两项为 `flex`；再点「继续横屏使用」，确认遮罩消失、转竖屏再横屏不再弹出、刷新后重新提示。真机 / App 内需另行确认。

### 5.2 竖屏兼容建议（H5 默认竖屏时一并给出）

确认项目按竖屏使用后，审查报告在「修复方案」里附上下列建议（按项目实际情况取舍，不是全部都要改）：

| 方面 | 建议 | 备注 |
|------|------|------|
| 竖屏视口矩阵 | 320×568、360×640、375×667、390×844、414×896、430×932；平板竖屏 768×1024 | 最小宽度 320 下无横向溢出；折叠屏展开后接近方形，**不会**命中 §5.1 的横屏遮罩（高度 > 480px） |
| 宽度适配 | 流式宽度（`%` / `flex`），不写死设计稿宽度；容器可加 `max-width` | 设计稿 393 宽只是参照基准 |
| 叠在大图上的元素（返回键、角标、浮层） | 位置用**百分比**（相对图片宽高比换算），尺寸保持 px | 写死 px 偏移时，屏宽变化后图片放大缩小而元素不动，会与图上文字错位 |
| 首屏大图 | 用 `padding-top: <高÷宽>%` 的比例占位容器，图片绝对定位铺满 | 图未加载完时高度不塌陷、加载后不跳动；**不要**用 `aspect-ratio`（iOS < 15 / Chrome < 88）或 `<img width height>`（iOS < 14 / Chrome < 79），盖不住 iOS 10 / Chrome 51 基线 |
| 高度 | 页面用 `min-height`，`100vh` 在前、`100dvh` 在后；文本容器用 `min-height` 而非固定 `height` | 系统 / 微信字体放大时不重叠、不截断 |
| 间距 | 基线含 iOS < 14.1 / Chrome < 84 时，flex 间距用 `margin` 代替 `gap` | 否则间距消失 |
| 安全区与底栏 | `viewport-fit=cover` + `env(safe-area-inset-*)`；`position: fixed` 底栏在软键盘弹出时单独验证 | 竖屏下最常见的遮挡问题 |
| 点击区域 | 视觉小于 44×44px 的按钮，用透明伪元素扩展热区，不改视觉 | 避免用 `inset`（iOS < 14.1），用 `left/right/top/bottom` |
| 横屏遮罩的实现细节 | 显示条件用纯 CSS 媒体查询，只卸载遮罩自身（关闭状态用一个布尔值），**不要卸载页面内容** | 转回竖屏后页面状态（表单内容、滚动位置）保留；并提供「继续横屏使用」关闭入口 |
| 宿主侧锁定 | 嵌入主应用 / 小程序时，优先由宿主锁定竖屏（小程序 `pageOrientation`、原生 App 方向设置） | 网页侧遮罩只是兜底 |

### 5.3 体验层检查项（H5 默认覆盖）

兼容性解决「能不能打开」，体验层解决「用起来顺不顺」。**H5 审查默认逐项过一遍**，命中的写入发现表（来源填「源码」或「运行」），按下表定级；项目处于脚手架 / mock 阶段、功能尚未接入的，标注「待接入时落实」而不是直接判缺陷。

**A. 影响线上可用性（优先）**

| # | 检查项 | 检查方法 | 定级 / 修复 |
|---|--------|---------|------------|
| 1 | 兼容数据与错误上报 | `grep -rnE 'onerror\|unhandledrejection\|sentry\|fundebug\|上报' src index.html`；有无 UA / 内核版本统计 | 无 → 🟡：基线与「值不值得修」只能靠 caniuse 估算。接入 `window.onerror`、`unhandledrejection`、资源加载失败上报，并记录 UA 与内核版本 |
| 2 | 异步状态：加载中 / 空数据 / 失败重试 / 断网 | `grep -rnE 'skeleton\|van-empty\|van-loading\|van-pull-refresh\|showToast\|showFailToast\|offline' src`；看请求封装有无超时 / 重试 / 断网提示 | 页面已有接口调用却缺 → 🟡（弱网下白屏或静止，用户以为坏了）。接口尚未接入的标「待接入时落实」 |
| 3 | **存储访问兜底** | `grep -rnE 'localStorage\|sessionStorage' src`，逐处确认在入口（`main.ts` / 路由守卫 / 请求拦截器）路径上是否有 `try/catch` | 入口路径未保护 → 🟡；**目标环境含下列情形时升 🔴**（入口抛错即白屏）。会抛错的情形：① iOS「阻止所有 Cookie」、沙箱 iframe、跨站 iframe 被禁存储时，访问 `window.localStorage` 抛 `SecurityError`；② Android WebView 未开启 DOM storage 时 `window.localStorage` 为 `null`，调用 `.getItem` 抛 `TypeError`；③ iOS ≤ 10 Safari 隐私模式与存储配额写满时，`setItem` 抛 `QuotaExceededError`（iOS 11+ 隐私模式可正常读写，仅为会话级）。表述以真机为准。读失败按「无 token」处理，写 / 删失败静默忽略 |
| 4 | 防重复提交 | 提交 / 支付 / 下单类按钮是否有 `disabled` / loading / 防抖；`grep -rnE ':disabled\|loading\|submitting' src/pages` | 缺 → 🟡（弱网连点产生重复数据）。用「执行期间忽略再次调用」的守卫 |
| 4′ | 表单离开确认（可选） | 长表单误触返回会丢内容 | **按项目取舍**，用户明确不要的不加；不要用 `beforeunload`（微信等 WebView 不触发）。给出建议即可，不记缺陷 |
| 5 | 微信缓存与返回（bfcache） | ① `curl -sI <域名>/<base>/index.html` 看 `Cache-Control`；② `grep -rn 'pageshow' src`；③ 资源文件名是否带 hash | HTML 被强缓存 → 🟡（发版后用户看旧页）：HTML 设 `no-cache`、`assets/` 长缓存（属服务器配置，需运维确认）；返回页面从 bfcache 恢复不会重跑入口脚本 → 在 `pageshow`（`event.persisted`）重新校验登录态、必要时刷新数据 |

## 6. 覆盖率口径

caniuse 地区数据**同时含桌面与移动**，H5 应计算「覆盖的移动用户 ÷ 全部移动用户」：

```bash
ALL_MOBILE="ios_saf >= 0, and_chr >= 0, and_uc >= 0, and_qq >= 0, samsung >= 0, op_mob >= 0, and_ff >= 0, baidu >= 0, kaios >= 0, op_mini all"
npx browserslist@latest --coverage=CN "$ALL_MOBILE"                      # 分母:全部移动用户
npx browserslist@latest --coverage=CN "ios_saf >= 12, and_chr >= 64"     # 分子:基线覆盖
```

参考数据（2026-09，移动用户内占比）：

| 基线 | 全球 | 中国 |
|------|------|------|
| iOS ≥ 12 + Android Chrome ≥ 64 | 94.2% | **86.3%** |
| 上一行 + UC / QQ 浏览器 | 95.4% | **99.1%** |

> **caniuse 局限**：`and_chr` 只含最新一个 Android Chrome 版本，`and_chr >= 51` 实际等于「最新版」，**低估** Android 老 WebView / 微信 X5·XWeb 的占比；Android 侧的「下探硬下限能多覆盖多少」不能用它估算，须用项目访问统计或 `chrome 51-84` 作粗略代理，并在报告中写明。iOS 侧用 `ios_saf` 版本区间可信。

**国内 H5 中 UC / QQ 浏览器约占移动用户 13%**，且为自研内核、无法按 Chrome 版本推算——国内项目 MUST 将其列为必测环境。
